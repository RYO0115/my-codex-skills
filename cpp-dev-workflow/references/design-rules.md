# 設計ルール

クラス・モジュールを新規作成・変更する前に必ず読むこと。実装より先に設計を固め、以下に違反する設計はユーザーへ報告する。

## 設計手順

1. 既存コードを調査し、同じ・似た機能が既にないか確認する(重複禁止)。
2. 責務を1つに絞ったクラス/モジュール単位に分割する。
3. 依存の方向を決める(下記「循環参照の禁止」)。
4. ハードコード・グローバル変数が必要になりそうなら、**実装せずにこの時点で理由を報告し指示を仰ぐ**。
5. インターフェース(公開ヘッダ)を先に決めてからテストを書く(testing.md)。

## 汎用性・拡張性

- 具象クラスに直接依存せず、差し替えたくなる箇所(I/O、外部デバイス、時刻取得など)は抽象クラス(純粋仮想インターフェース)経由で注入する(依存性注入)。テストでモックに差し替えられることが基準。
- 「今の用途専用」の決め打ち実装を避ける。ただし過剰な抽象化もしない: **差し替え・追加が現実に想定される軸だけ**を抽象化する。

## 循環参照の禁止

- モジュール(ディレクトリ/ライブラリ)間の依存は一方向のみ。A→B と B→A の同時依存は設計で排除する。
- 相互参照が必要に見えた場合の解決順: (1) 共通部分を第3のモジュールへ抽出 → (2) 片方をインターフェース(抽象クラス)化して依存を逆転 → (3) コールバック/Observer で通知方向を分離。
- `std::shared_ptr` の相互所有は禁止(リーク)。親→子は `unique_ptr`/`shared_ptr`、子→親は生ポインタ参照または `weak_ptr`。
- ヘッダの相互 include はコンパイルエラーの元。前方宣言で切る。

## 重複実装の禁止

- 実装前に既存コードを Grep して同種の処理を探す。あれば再利用・共通化する。
- 同じロジックが2箇所に現れたら、共通関数・基底クラス・テンプレートへ抽出する。コピペ改変は禁止。

## ハードコードの禁止

- マジックナンバー・固定パス・URL・タイムアウト値などをコードに直接書かない。
- 定数は名前付き `constexpr`(`kMaxRetryCount` など)としてヘッダまたは設定構造体に集約する。
- 実行時に変わりうる値は設定ファイル・コンストラクタ引数・コマンドライン引数で注入する。
- どうしてもハードコードが必要な場合: **実装せず、なぜ必要かを設計段階でユーザーに報告し、指示を受けてから**書く。

## グローバル変数の禁止

- グローバル変数・シングルトン・`static` なミュータブル状態は原則禁止。状態はクラスに持たせ、必要な箇所へ参照を渡す。
- `constexpr` な定数はグローバルでよい。
- どうしても必要な場合: ハードコードと同様、**設計段階で理由を報告して指示を仰ぐ**。

マルチスレッドが関わる設計は `thread-safety.md` も併読すること。
