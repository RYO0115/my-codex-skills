# テストの詳細方針

## いつテストを追加するか

機能を**追加・修正・削除**したら毎回。純粋な内部リファクタ（外部の振る舞いが変わらない）だけは対象外。判断に迷ったら追加する。

## テストの種類の使い分け

| 検証したいもの | 種類 | 例のツール |
|---------------|------|-----------|
| ブラウザでの見た目・操作（HTMX/JS の挙動含む） | UI テスト | Playwright |
| ロジック単体を決定的に検証（ランダム性・日時条件など UI 越しでは検証しづらいもの） | ユニットテスト | pytest |

推奨ディレクトリ構成:

```
tests/
├── unit/     # サービス層など、決定的なロジックの単体テスト
└── ui/       # ブラウザ操作・表示のテスト
```

## テスト出力ラッパー（必須）

テスト件数に比例して成功時の進捗表示が増えると、エージェントが読む必要のない出力で
tokenを消費する。すべてのPythonプロジェクトで、pytestを直接呼ばずテストラッパーを
唯一の実行入口にする。

1. README・CI・`scripts/`・`pyproject.toml` を調べ、プロジェクト既定のラッパーがあれば使う。
2. なければ最初のテスト実行前に作る。配置とコマンド名はプロジェクト規約に合わせる。
3. ローカル手順、CI、PRテンプレートなどにあるrawのpytestコマンドをラッパーへ統一する。
4. 単一ファイル、テスト名、pytestオプションもラッパーへ渡す。作成後はrawのpytestを
   一時的な確認にも使わない。

ラッパーは次をすべて満たすこと。

- 全件成功かつskipなし: テスト件数と所要時間を含む1行程度の要約だけを標準出力へ出す。
- skipあり、Fail、収集エラー: pytestの標準出力・標準エラーを省略せず再表示する。
- pytestの終了コードをそのまま返し、失敗を成功扱いにしない。
- 通常のpytest引数を透過的に受け取る。
- 全出力をメモリへ保持せず一時ファイルへ保存し、大規模テストでも安定して動く。
- 成功時の抑制、skip検出、Fail時の出力と終了コードの維持を自動テストで固定する。

## 完了前の確認

- プロジェクト既定のテストラッパーを実行して**全テスト green**を確認してから完了報告する。
- テストが落ちている場合は、出力を添えて落ちている事実を正直に報告する。

## 既存テストとの関係

- 変更が既存テストの対象範囲内なら、新規ファイルを作らず既存テストを修正する。
- テスト一覧ドキュメントがあるプロジェクトでは、追加・変更したテストケースを追記する。
